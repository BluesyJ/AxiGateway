# AxiGateway 项目立项报告草案

日期为 2026-11-12。供接手 Codex 补充和用户审批。现有阶段归属为 P4.2「切换阿汐」，阶段调整和新增能力尚待批准。工程现状及出处见 [工程交接](ENGINEERING_HANDOFF.md)，阶段定义以 [ROADMAP](ROADMAP.md) 为准。

## 项目背景与价值

用户运行 AstrBot QQ 机器人，主聊天、备用模型和插件可能独立访问模型供应商。当前只能从多个配置和日志追踪调用。用户希望统一入口，在聊天异常时快速找到对应请求，查看实际输入、回复、耗时和错误原因，同时了解用量与估算费用。

项目已经完成本机元数据采集和主聊天接入，具备继续建设的基础。后续投入应直接改善使用和排错体验，并以可核验的性能与可靠性边界支持长期使用。

## 目标及受众

近期服务于单用户 Windows 本机使用，交付可启动、可查询、可诊断的版本。中期支持便捷安装升级、明确的数据保留与清理、稳定的模型接入和凭据管理。长期建设通用、可维护、可部署的开源 AI 流量监测工具，客户端不限于 AstrBot。

具体收益包括能够定位一次调用、解释失败、判断模型等待与网关开销、发现采集缺口，并减少日常操作步骤。上线后可由用户按实际排错任务检验这些收益。

## 已有基础与差距

已有 LiteLLM Proxy、严格环境检查、SQLite WAL 事件库、只读控制台、来源化用量与费用统计。主聊天经过网关。剩余客户端入口尚未全部验收；正文、首 token 指标和具体错误诊断尚未实现；拒绝和丢失仍有逐条不可见边界；产品打包入口仍含 legacy 配置。

代码审查重点为回调可提供哪些正文和计时信息、如何处理流式中断及重复事件、如何避免新增记录功能拖慢模型请求。现有回调能力不足时，应提出具体扩展方案及影响，按 SPEC 变更流程决定。

## 建议的产品范围

| 能力 | 可验收的用户结果 | 需要决定的范围 |
|---|---|---|
| 完成接入 | 每个已启用 LLM 入口的去向明确，有对应证据 | 剩余入口是否接入或暂缓 |
| 单次请求详情 | 列表打开一条后看输入、回复、结果和可用错误原因 | 正文类型、失败边界、重试关联 |
| 正文生命周期 | 开关和采集状态清楚，可清理，过期处理可验 | 保留天数、单条/总容量、截断及清理规则 |
| 界面简化 | 默认进入实际请求，演示功能有明确开发用途 | 客户端汇总和健康详情的入口 |
| 性能验证 | 给出明确并发下的耗时、成功率、记录完整性 | 目标负载、样本数、可接受增量 |
| 可用交付包 | 新机器按文档安装并启动当前架构 | Windows 本机包与 P5 容器化的先后 |

正文记录需始终过滤凭据，并明确输入内容、回复内容和部分回复的保存状态。不要用统一“成功”掩盖采集失败。当前 localhost 管理面在增加敏感正文后，需要重新评估访问边界及其与 P6 登录的关系。

## 建议实施顺序与路线图关系

先完成 P4.2 的剩余入口结论，再优先解决单次请求正文与错误排查，随后在完整新链路上进行有限并发与延迟验证，最后整理易用启动及发布方式。这是建议顺序。

原 P4.3 干净窗口对账、P4.4 本地模型、P5 容器化、P6 登录、P7 模型与 Key 管理、P8 发布准备继续保留。正文与请求详情目前没有明确阶段归属。接手 Codex 应提交归属或调整提案，说明为何改变顺序、对应哪些现有阶段，由用户批准后写入 ROADMAP。

## 验收和资源预算

下一次实现前应分别为成功、上游失败、流式中断、并发区分与正文清理选择必要用例，明确输入、预期结果、观察位置和停止条件。验证规模服务于是否继续日常使用的决策，不要求无限扩展覆盖。

开发人力为用户决策与验收、开发 agent 实现、审查 agent 评审。当前没有可支撑完整项目工期或总费用的估算。需先确定范围，再按每项任务填写最多轮次、用例数、天数和真实调用额度。不得将助手先前提出的“7 天正文保留期”等建议直接当成批准条件。

## 主要风险及决策

1. 元数据架构不等于正文生命周期支持，需要设计容量、迁移、清理及失败状态。
2. 当前尽力投递语义无法保证所有请求完整留痕，需要明确产品承诺与成本。
3. 回调首 token、部分回复和重试关联能力须由固定版本契约证明。
4. 现有严格运行锁及 Windows DPAPI 给跨平台、容器化和升级带来实际工作量。
5. 工作区大量未提交内容、旧入口文档及旧打包配置会影响迁移和发布完整性。
6. 许可证及管理认证方式待定，正式发布前需完成选择和验证。
